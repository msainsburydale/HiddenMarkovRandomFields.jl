Unconditional and conditional simulation ​

simulatehiddenpotts and simulatepotts offer two kinds of simulation:

  • Unconditional simulation draws the labels from the Potts model, and then the data from the emission distributions.

  • Conditional simulation starts from incomplete data, with observed values and missing values . It draws the labels from  , and then the missing values from the emission distributions given their labels. For the Potts model, the known labels are held fixed and the others are simulated.

This allows, for example, zero-inflated or bounded data (as in the sea-ice example in Examples) to be modelled with Beta emissions for the interior of and Dirac(0.0) and Dirac(1.0) for the boundary values.

Swendsen–Wang updates ​

Gibbs sampling changes one pixel at a time. Near and above , large clusters of one label rarely change, and Gibbs sampling mixes slowly. The Swendsen–Wang algorithm (Swendsen and Wang, 1987) changes whole clusters at once, using the Edwards–Sokal representation of the model (Edwards and Sokal, 1988). Each sweep has two steps:

  1. Every pair of neighbours with equal labels is joined by a bond independently with probability  . The bonds partition the grid into clusters.

  2. Each cluster draws a new label, with probability proportional to the product of the likelihood weights of its pixels, . A cluster that contains a fixed pixel keeps that pixel's label.

When there are data, the likelihood weights make it hard for large clusters to change label. This is the usual difficulty of Swendsen–Wang with an external field (Higdon, 1998), and one reason the two updates are combined. Each MCMC iteration is a chequerboard Gibbs sweep, preceded every sw_every iterations by a Swendsen–Wang sweep. The default, sw_every = 1, runs both in every iteration, and sw_every = 0 gives Gibbs sampling only.

Initialisation ​

The chains start close to a typical state, to shorten burn-in:

  • Fixed pixels take their known labels.

  • Observed pixels take their maximum-likelihood labels.

  • Missing pixels are filled outward from the assigned pixels by a breadth-first flood fill, after 1% of them are seeded at random. Below , each pixel is drawn from the Potts conditional distribution given its assigned neighbours. Above , each pixel takes the most common label among its assigned neighbours.

With no data at all (unconditional simulation), the labels start uniformly at random below . Above , they start as random blocks with a few random perturbations.

Multiple chains, threads and reproducibility ​

The keyword argument nchains sets the number of independent chains, and ntasks (by default, the number of Julia threads) the number of tasks that run in parallel. The chains are distributed over the tasks. When there are fewer chains than tasks, the remaining tasks share the work of each chain, for grids of roughly 64 × 64 pixels or more; see Performance.

To share the work of a chain, the grid is divided into blocks of consecutive columns:

  • Gibbs sweeps. The blocks are updated in parallel, since the pixels of one chequerboard colour are conditionally independent.

  • Swendsen–Wang sweeps. Clusters are first found within each block in parallel. The clusters that cross block boundaries are then joined, and finally every cluster draws its new label in parallel.

Each block has its own random-number generator, seeded from rng, so the results depend only on rng, not on the number of tasks or threads.

Each chain can have its own parameters: β can be a vector with one value per chain, and the emission distributions a vector with one vector of distributions per chain. One call then simulates, for example, the training data of a neural estimator, with each field drawn from its own parameter values; see Examples.

The keyword argument save_at selects the iterations whose states are returned, which allows, for example, burn-in to be assessed. Iteration 0 is the initial state.

To keep chains between calls, use the persistent-chain interface described in API. This is useful, for example, to continue the chains under new parameter values in a Monte Carlo EM algorithm (Wei and Tanner, 1990), such as the neural EM algorithm (Sainsbury-Dale et al., 2025).

GPU sampling ​

Set the keyword argument backend to a KernelAbstractions.jl backend, such as CUDABackend() after using CUDA. Then simulatehiddenpotts and simulatepotts run all nchains chains together on the GPU, and return arrays on the GPU. Loading a GPU package loads KernelAbstractions, which loads the package extension that holds the GPU code. For persistent chains on a GPU, use PottsChains.

The GPU runs the same algorithms as the CPU:

  • Initialisation. The chains are initialised on the CPU, as described above, and then copied to the GPU.

  • Gibbs sweeps. One kernel per chequerboard colour updates every pixel of that colour in every chain, with each GPU thread updating two chains. The labels are stored pixel by pixel, with the chains of each pixel next to each other, so that neighbouring GPU threads read and write neighbouring bytes. For a few chains on a small grid, consecutive sweeps run in one kernel, which keeps each chain's labels in on-chip memory.

  • Swendsen–Wang sweeps. The bonds of all chains are opened in parallel, and their clusters are found by union-find with atomic operations. Each cluster then sums the log-likelihood weights of its pixels, and draws its new label from these sums. The sums are accumulated in fixed point with integer atomics, so they do not depend on the order of the additions. Each GPU thread first adds up the weights of a few consecutive pixels of the same cluster, which reduces contention when one cluster covers most of the grid.

  • Data. The missing values are drawn on the GPU for Normal, LogNormal, Uniform, Exponential, Gamma, Beta and Dirac emissions. For other distributions, they are drawn on the CPU and copied back.

Random numbers come from the counter-based generators Philox2x32-10 and Philox4x32-10 (Salmon et al., 2011), indexed by the pixel, the chain and the step of the algorithm. Results are therefore reproducible given rng, and don't depend on how the work is divided among GPU threads. They differ from those of the CPU sampler, though.

The GPU code is written with KernelAbstractions and tested on NVIDIA GPUs with CUDA.jl. Other GPUs with 64-bit atomic operations, e.g. AMD GPUs with AMDGPU.jl, may also work. Apple GPUs (Metal.jl) won't, since they lack 64-bit atomics. At most 32 labels are supported. See Performance for timings.
